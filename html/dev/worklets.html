    11 ワークレット

    11.1 導入

    ワークレットは、特定の実装モデルを必要とせずに、メインのJavaScript実行環境から独立してスクリプトを実行するために使用できる仕様のインフラの一部である。

    ここで指定したワークレットインフラは、ウェブ開発者が直接使用することはできない。その代わりに、他の仕様はそのワークレットインフラに基づいて構築され、ブラウザー実装パイプラインの特定の部分で実行するために特化された、直接使用可能なワークレットタイプを作成する。

    11.1.1 動機

    レンダリング、または音声出力などの実装パイプラインのその他の機微な部分に拡張ポイントを許可することは困難である。拡張ポイントがWindow上で利用可能なAPIへの完全なアクセスを伴う形で設けられるなら、エンジンは、それらのフェーズの途中で何が起こり得るかについて従来保持していた前提を放棄する必要がある。例えば、レイアウトフェーズ中、レンダリングエンジンはDOMが変更されないと想定する。

    さらに、Window環境で拡張ポイントを定義すると、ユーザーエージェントはWindowオブジェクトと同じスレッドで作業を実行するよう制限される。（ただし、実装がスレッドセーフなAPIを可能にする複雑でオーバーヘッドの大きいインフラと、スレッドのjoinに関する保証を追加する場合は除く。）

    ワークレットは、ユーザーエージェントが現在依存している保証を維持しながら、拡張ポイントを可能にするよう設計されている。これは、WorkletGlobalScopeのサブクラスに基づく新しいグローバル環境を通じて実現される。

    ワークレットはウェブワーカーに類似している。ただし、次の点が異なる：

    • スレッド非依存である。すなわち、各ワーカーのように専用の個別スレッドで実行するよう設計されているわけではない。実装は、選択した任意の場所（メインスレッドを含む）でワークレットを実行できる。

    • 並列処理を目的として、グローバルスコープの重複インスタンスを複数持つことができる。

    • イベントベースのAPIを使用しない。その代わり、クラスはグローバルスコープに登録され、そのメソッドはユーザーエージェントによって呼び出される。

    • グローバルスコープ上で縮小されたAPIサーフェスを持つ。

    • それらのグローバルオブジェクトの存続期間は他の仕様によって定義され、多くの場合、実装定義の方法で定義される。

    ワークレットは比較的オーバーヘッドが大きいため、控えめに使用するのが最善である。このため、与えられたWorkletGlobalScopeは複数の個別のスクリプト間で共有されることが想定されている。（これは、単一のWindowが複数の個別のスクリプト間で共有される方法に類似している。）

    ワークレットは、さまざまなユースケースに対応する汎用技術である。CSS Painting APIで定義されているものなど、一部のワークレットは、ステートレスで、冪等で、短時間で実行される計算を対象とする拡張ポイントを提供しており、これらには次のいくつかの節で説明する特別な考慮事項がある。一方、Web Audio APIで定義されているものなど、その他のものは、ステートフルで長時間実行される操作に使用される。[CSSPAINT] [WEBAUDIO]

    11.1.2 コードの冪等性

    ワークレットを使用する一部の仕様は、ユーザーエージェントが複数のスレッドにわたって作業を並列化すること、または必要に応じてスレッド間で作業を移動したりできるようにすることを意図している。これらの仕様では、ユーザーエージェントは、ウェブ開発者が提供したクラス上のメソッドを実装定義の順序で呼び出す場合がある。

    その結果、相互運用性の問題を防ぐために、そのようなWorkletGlobalScopeにクラスを登録する著者は、コードを冪等にすべきである。つまり、そのクラス上のメソッドまたはメソッド群は、特定の入力が与えられた場合に同じ出力を生成すべきである。

    この仕様は、著者が冪等な方法でコードを記述するよう促すために、次のテクニックを使用する：

    • グローバルオブジェクトへの参照は利用できない（すなわち、WorkletGlobalScope上にはselfに相当するものがない）。

      これは、ワークレットが最初に仕様化されたときの意図であったが、globalThisの導入によって、もはや正しくなくなっている。詳細な議論については、issue #6059を参照。

    • コードはモジュールスクリプトとして読み込まれ、その結果、コードは厳格モードで実行され、グローバルプロキシを参照する共有のthisは存在しない。

    これらの制限は共に、2つの異なるスクリプトがグローバルオブジェクトのプロパティを使用して状態を共有することを防ぐ助けとなる。

    さらに、ワークレットを使用し、実装定義の動作を許可することを意図する仕様は、次の要件に従わなければならない：

    • それらは、ユーザーエージェントが各Workletにつき少なくとも2つのWorkletGlobalScopeインスタンスを常に持ち、クラス上のメソッドまたはメソッド群を特定のWorkletGlobalScopeインスタンスにランダムに割り当てることを要求しなければならない。これらの仕様は、メモリ制約下でオプトアウトする選択肢を提供してもよい。

    • これらの仕様は、ユーザーエージェントが任意の時点でWorkletGlobalScopeサブクラスのインスタンスを作成および破棄できるようにしなければならない。

    11.1.3 投機的評価

    ワークレットを使用する一部の仕様は、ユーザーエージェントの状態に基づいて、ウェブ開発者が提供したクラス上のメソッドを呼び出すことができる。スレッド間の並行性を高めるため、ユーザーエージェントは、将来起こり得る状態に基づいて、メソッドを投機的に呼び出してもよい。

    これらの仕様では、ユーザーエージェントは、現在のユーザーエージェントの状態に対応する引数だけでなく、任意の引数を使用して、任意の時点でそのようなメソッドを呼び出す場合がある。このような投機的評価の結果は、直ちには表示されないが、ユーザーエージェントの状態が予測された状態と一致した場合に使用できるよう、キャッシュされることがある。これにより、ユーザーエージェントとワークレットのスレッド間の並行性を高めることができる。

    その結果、ユーザーエージェント間の相互運用性のリスクを防ぐために、そのようなWorkletGlobalScopeにクラスを登録する著者は、コードをステートレスにすべきである。つまり、メソッドを呼び出すことの唯一の効果はその結果であるべきであり、可変状態の更新などの副作用であってはならない。

    コードの冪等性を促進する同じテクニックは、著者がステートレスなコードを記述することも促進する。

    11.2 例

    これらの例では、偽ワークレットを使用する。Windowオブジェクトは2つのWorkletインスタンスを提供し、それぞれが独自のFakeWorkletGlobalScopeの集合内でコードを実行する：

    window.fakeWorklet1
    偽ワークレットの1つを返す。
    window.fakeWorklet2
    別の偽ワークレットを返す。

    これらはいずれも、ワークレットのグローバルスコープ型がFakeWorkletGlobalScopeに設定され、ワークレットの宛先型が"fakeworklet"に設定されている。ユーザーエージェントは、各ワークレットにつき少なくとも2つのFakeWorkletGlobalScopeインスタンスを作成すべきである。

    "fakeworklet"は、実際にはFetchにおける有効な宛先ではない。しかし、これは、実際のワークレットが一般に、それぞれのワークレット型に固有の宛先を持つことを示している。[FETCH]

    FakeWorkletGlobalScope内では、次のグローバルメソッドを利用できる：

    registerFake(type, classConstructor)
    classConstructorで与えられるJavaScriptクラスを、ユーザーエージェントが後でtypeによって指定された何らかの操作を実行するときに使用するために登録する。

    11.2.1 スクリプトの読み込み

    偽ワークレット1にスクリプトを読み込むため、ウェブ開発者は次のように記述する：

    window.fakeWorklet1.addModule('script1.mjs');
window.fakeWorklet1.addModule('script2.mjs');

    どちらのスクリプトのフェッチが先に完了し、最初に実行されるかはネットワークのタイミングに依存することに注意する。それはscript1.mjsまたはscript2.mjsのいずれかであり得る。これは一般に、投機的評価への準備に関する提案に従っている場合、ワークレットへの読み込みを意図して適切に記述されたスクリプトでは問題にならない。

    ウェブ開発者が、スクリプトが正常に実行され、いくつかのワークレットに読み込まれた後にのみタスクを実行したい場合、次のように記述できる：

    Promise.all([
    window.fakeWorklet1.addModule('script1.mjs'),
    window.fakeWorklet2.addModule('script2.mjs')
]).then(() => {
    // Do something which relies on those scripts being loaded.
});

    スクリプトの読み込みに関するもう1つの重要な点は、コードの冪等性に関する節で説明したとおり、読み込まれたスクリプトは1つのWorkletにつき複数のWorkletGlobalScopeで実行され得ることである。特に、偽ワークレット1および偽ワークレット2に関する上記の仕様は、これを要求する。そこで、次のようなシナリオを考える：

    // script.mjs
console.log("Hello from a FakeWorkletGlobalScope!");
    // app.mjs
window.fakeWorklet1.addModule("script.mjs");

    これにより、ユーザーエージェントのコンソールに次のような出力が生じることがある：

    [fakeWorklet1#1] Hello from a FakeWorkletGlobalScope!
[fakeWorklet1#4] Hello from a FakeWorkletGlobalScope!
[fakeWorklet1#2] Hello from a FakeWorkletGlobalScope!
[fakeWorklet1#3] Hello from a FakeWorkletGlobalScope!

    ユーザーエージェントがある時点で、FakeWorkletGlobalScopeの3番目のインスタンスを強制終了して再起動することを決定した場合、その際、コンソールには再び[fakeWorklet1#3] Hello from a FakeWorkletGlobalScope!が出力される。

    11.2.2 クラスの登録およびそのメソッドの呼び出し

    ウェブ開発者による偽ワークレットの意図された使用法の1つが、ブール否定という非常に複雑なプロセスをカスタマイズできるようにすることであるとする。ウェブ開発者は、そのカスタマイズを次のように登録する場合がある：

    // script.mjs
registerFake('negation-processor', class {
  process(arg) {
    return !arg;
  }
});
    // app.mjs
window.fakeWorklet1.addModule("script.mjs");

    このように登録されたクラスを利用するため、偽ワークレットの仕様は、Worklet workletを受け取り、trueの反対を求めるアルゴリズムを定義できる。これは、workletのグローバルスコープのいずれかに"negation-processor"型として登録された任意のクラスのprocessメソッドを引数trueで呼び出し、その後、その結果を何らかの方法で使用する。

    11.3 インフラ

    11.3.1 グローバルスコープ

    WorkletGlobalScopeのサブクラスは、特定のWorkletに読み込まれたコードを実行できるグローバルオブジェクトを作成するために使用される。

    他の仕様は、WorkletGlobalScopeをサブクラス化し、クラスを登録するためのAPIおよび、それぞれのワークレット型に固有のその他のAPIを追加することを意図している。

    11.3.1.1 エージェントおよびイベントループ

    各WorkletGlobalScopeは、それぞれ独自のワークレットエージェントに含まれており、そのエージェントには対応するイベントループがある。しかし、実際には、これらのエージェントおよびイベントループの実装は、他の大半のものとは異なると想定されている。

    理論上、実装はWorkletGlobalScopeの各インスタンスに個別のスレッドを使用でき、このレベルの並列性を可能にするにはエージェントを使用するのが最適であるため、各WorkletGlobalScopeに対してワークレットエージェントが存在する。ただし、それらの[[CanBlock]]の値はfalseであるため、エージェントとスレッドが1対1で対応する必要はない。これにより、実装は、ワークレットに読み込まれたスクリプトを任意のスレッドで実行でき、これには、[[CanBlock]]がfalseである他のエージェントからのコードを実行しているスレッド、例えば類似オリジンのウィンドウエージェント（"メインスレッド"）のスレッドも含まれる。これとは対照的に、専用ワーカーエージェントは、[[CanBlock]]の値がtrueであるため、事実上、専用のオペレーティングシステムスレッドを必要とする。

    ワークレットのイベントループも、いくぶん特殊である。それらは、addModule()に関連付けられたタスク、ユーザーエージェントが著者定義のメソッドを呼び出すタスク、およびマイクロタスクにのみ使用される。したがって、イベントループ処理モデルはすべてのイベントループが継続的に実行されることを規定しているが、実装は、著者が提供したメソッドを呼び出し、そのプロセスにマイクロタスクチェックポイントを実行させるだけの、より単純な戦略を用いて、観測可能な結果が等価になるようにできる。

    Workletクラスは、関連付けられたWorkletGlobalScopeにモジュールスクリプトを追加する機能を提供する。その後、ユーザーエージェントはWorkletGlobalScopeに登録されたクラスを作成し、それらのメソッドを呼び出すことができる。

    Workletインスタンスを作成する仕様は、各インスタンスについて次の事項を指定しなければならない：

    • そのワークレットグローバルスコープ型。これはWorkletGlobalScopeを継承するWeb IDL型でなければならない。および

    • そのワークレットの宛先型。これは宛先でなければならず、スクリプトのフェッチ時に使用される。

    await worklet.addModule(moduleURL[, { credentials }])

    moduleURLで指定されたモジュールスクリプトを読み込み、workletのすべてのグローバルスコープで実行する。また、この処理の一環として、ワークレット型に応じて追加のグローバルスコープを作成することもできる。スクリプトがすべてのグローバルスコープで正常に読み込まれ、実行されると、返されるプロミスは実行される。

    credentialsオプションは、スクリプトのフェッチ処理を変更するために資格情報モードに設定できる。デフォルトは"same-origin"である。

    スクリプトまたはその依存関係のフェッチに失敗すると、返されるプロミスは"AbortError" DOMExceptionで拒否される。スクリプトまたはその依存関係の解析でエラーが発生すると、返されるプロミスは解析中に生成された例外で拒否される。

    11.3.3 ワークレットの存続期間

    Workletの存続期間には特別な考慮事項はなく、Windowなど、それが属するオブジェクトに結び付けられている。

    WorkletGlobalScopeの存続期間は、少なくとも、それを含むワークレットグローバルスコープを有するDocumentに結び付けられている。特に、Documentを破棄すると、対応するWorkletGlobalScopeは終了し、ガベージコレクションが可能になる。

    さらに、対応するワークレット型を定義する仕様で別段の定めがない限り、ユーザーエージェントは任意の時点で、特定のWorkletGlobalScopeを終了させてもよい。例えば、ワークレットエージェントのイベントループにキューに入っているタスクがない場合、ユーザーエージェントがそのワークレットを使用する予定の保留中の操作を持たない場合、またはユーザーエージェントが無限ループもしくは課された時間制限を超えるコールバックなどの異常な操作を検出した場合に、終了させることがある。

    最後に、特定のワークレット型に関する仕様は、特定のワークレット型についてWorkletGlobalScopeをいつ作成するかに関する、より詳細な情報を示すことができる。たとえば、例に示すように、ワークレットコードを呼び出す特定の処理中に、それらを作成することがある。
